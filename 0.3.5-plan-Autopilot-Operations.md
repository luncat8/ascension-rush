# Plan 0.3.5 — Autopilot Operations Deck

## Goal

Turn autopilot from a builder checkbox into a clear pad-to-pad transport
workflow. The player can choose departure and destination pads, dispatch a
one-way or return flight, inspect completed flights, and promote a successful
flight into an automatic route. Routes wait for a compatible free rocket and
payload instead of silently changing the active flight.

This release is about operations UX and reliable state transitions. It records
the cost and revenue inputs needed for later profitability reporting, but does
not attempt 0.4's contract market, detailed part inventory, repair, or route
profit optimization.

## Product rules

### Rocket, rocket type, and availability

Use three distinct terms in code and UI:

- A **rocket type** is a named, immutable build template: stage count, stage
  fuel capacities, stage strengths, payload limit, and autopilot profile. A
  route points to a type, not to the mutable builder form.
- A **rocket** is a fleet instance of one type. It has an ID, current pad,
  current fuel by stage, stage-alive state, status, and current route/flight
  assignment. Status is `available`, `queued`, `flying`, `turnaround`, or
  `lost`.
- A rocket is **available** only when it is intact enough to launch, is at the
  route's next departure pad, is not assigned to another flight, and satisfies
  that leg's fuel policy. Matching is deterministic: use the oldest available
  compatible rocket ID so route behavior can be tested and explained.

A safely landed rocket remains a fleet instance. Stages separated in flight do
not reappear. If its surviving stack no longer matches the type's launch
configuration, it cannot begin another full-template leg until turnaround has
restored the missing stages. In 0.3.5, turnaround is immediate while the game
is at the operations deck and charges the same structure cost as the replaced
stages; later part inventory and repair can replace this simplified rule.
A crash marks the instance `lost`; it is never reused by a route.

The first run starts with the existing reference rocket type and one available
instance at the selected world's home pad. Creating another instance is an
explicit **Build rocket** action with its estimated price, never a hidden route
side effect.

### Payload availability

0.3.5 has no contract market, so do not invent customer demand. A dispatch or
route specifies payload mass for each direction. A positive mass is considered
available when it fits the selected rocket type and the player can afford the
leg; zero is an intentional repositioning flight. Keep a named
`payloadProvider` boundary so 0.4 can replace this provisional rule with
contracts/cargo inventory without changing the route scheduler.

The UI says why a route is waiting: `NO ROCKET AT NORTH PAD`, `ROCKET BUSY`,
`PAYLOAD EXCEEDS CAPACITY`, `NEEDS REFUEL`, or `INSUFFICIENT FUNDS`. Never use a
generic disabled state when a specific cause is known.

### One-way and return missions

A **one-way** dispatch contains one leg: start to destination.

A **return** dispatch contains two ordered legs: start to destination, then
destination back to start. The return leg is not a second unrelated route. The
mission remains active between touchdowns, reports progress as `LEG 1 OF 2`
and `LEG 2 OF 2`, and completes only when the rocket returns or the mission
fails.

Return missions offer a plain fuel policy:

- **Refuel at destination** restores the surviving stages up to the rocket
  type's configured capacities before the return launch and charges only fuel
  actually loaded. Missing stages still require normal turnaround. Show the
  expected maximum refuel cost before dispatch.
- **No destination refuel** preserves the exact fuel and surviving-stage state
  from the outbound touchdown. The return launch uses that state; no fuel or
  stages are added. Reject the return launch if the remaining stack cannot
  meet the ordinary launch TWR gate, and leave the rocket safely parked with a
  clear `RETURN BLOCKED` result. Do not fake feasibility with doubled delta-v
  or reset the rocket between legs.

The outbound payload is unloaded after a successful target-pad touchdown. The
return payload is then loaded from its own configured mass. Payload mass must
not remain aboard accidentally between legs. A wrong-pad landing or unsafe
landing ends the whole return mission; it does not teleport the rocket or
continue with the next leg.

## Operations-deck UX

Replace the long builder-first flow with an operations panel that works on
small screens and keeps the map visible where possible. Use three top-level
views with real buttons and an accessible selected state:

1. **Dispatch**
2. **Routes**
3. **Flight log**

Retain **Rocket workshop** as a secondary action from Dispatch and a route's
rocket-type picker. The existing detailed stage controls live there rather
than competing with routine autopilot dispatch.

### Dispatch view

The primary card follows the order in which a player makes the decision:

1. **From** pad selector.
2. Direction/swap button.
3. **To** pad selector; selecting the same pad is invalid.
4. **One way / Return** segmented control.
5. For Return, **Refuel at destination / Use remaining fuel** control.
6. Outbound payload and, for Return, return payload.
7. Rocket type and a concrete available rocket at the start pad.
8. Autopilot profile.
9. Read-only summary: distance per leg, total legs, payload, estimated maximum
   cash required, rocket location/status, and any blocking reason.
10. One dominant action: **Send on autopilot**.

Pad options show pad name and wrapped surface distance. The map highlights the
selected start, destination, shortest wrapped direction, and return arrow when
applicable. **Swap** exchanges pads and directional payloads without resetting
rocket type, profile, or fuel policy.

Do not call an autopilot dispatch “Launch · full throttle.” On successful
click, lock a complete mission snapshot, switch to flight, focus the map, and
show mission progress in the flight HUD. Duplicate clicks must not create
multiple flights.

The start selector is not cosmetic. It lists all pads, then the rocket picker
and send action reflect fleet availability at that pad. Selecting a pad with no
rocket provides **Build rocket here** or a route-friendly waiting state; it
never silently moves the current rocket.

### Routes view

Show saved routes as compact cards with:

- route name and enabled/paused switch;
- start ⇄ end (or start → end) and next leg;
- refuel policy;
- outbound/return payload;
- assigned rocket type;
- status and specific wait reason;
- completed/failed leg counts and last-run time;
- **Send next**, **Pause**, **Change rocket type**, and **Delete** actions.

Creating a route is possible from the current Dispatch form and from a
completed flight-log item. Creating from a log pre-fills the exact flown pads,
direction, payload, rocket type/build snapshot, and autopilot profile. It does
not enable the route until the player reviews and saves it.

**Change rocket type** opens a compact picker with capacity, stage count,
launch TWR on this world, estimated leg cost, and location/availability. The
change applies only while the route has no flying leg. If the new type cannot
carry either directional payload, keep the dialog open and explain the limit.
Changing a route's type never mutates past log records or an already-dispatched
mission snapshot.

An enabled route requests one leg at a time. At the operations deck, a small
scheduler chooses the oldest ready route (`createdAt`, then route ID), reserves
one matching rocket atomically, and offers/starts that flight. Because the
current game has one foreground simulation, only one route flight can be
flying at once; other routes remain visibly queued. There is no hidden
background physics simulation.

Default automation policy is **confirm before launch** so the player is not
pulled out of the deck unexpectedly. A per-route **Auto-launch when ready**
switch may skip that confirmation after the route has completed one successful
leg. Auto-launch is always paused while a modal/workshop is open and can be
cancelled during a short visible countdown. This keeps “automatic route” useful
without making the UI hostile.

For a return route, the next direction alternates only after a successful leg.
For a one-way route, another run requires a compatible rocket at the start;
the completed rocket remains at the destination and is not teleported back.

### Flight log view

Store every completed leg, including failures, as an append-only snapshot.
Newest entries appear first. Each row shows:

- completion time and status;
- start → intended destination and actual landing pad;
- rocket instance and rocket type names;
- payload and autopilot profile;
- elapsed flight time;
- touchdown speeds and target error;
- fuel used and fuel remaining;
- revenue, fuel cost, structure/turnaround cost, autopilot fee, and net cash
  delta when known;
- return-mission leg number when applicable.

The main action on a usable record is **Create route from flight**. Disable it
with an explanation when the referenced rocket type no longer exists; offer
**Restore type from snapshot** rather than guessing another build.

Keep raw financial fields even though profitability UI is deferred. Future
profitability can calculate revenue minus fuel, turnaround, fees, repair,
capital depreciation, and idle time from records without migrating a prose
report. 0.3.5 may show the already-known per-flight cash delta, but must not
label it route profit or forecast future earnings.

Provide useful empty states: how to send the first flight, why no routes exist,
and that failed flights also appear in the log. Cap the in-memory log at a named
limit (for example 200 legs) and discard oldest entries; route totals remain
separate counters.

## State model

Add a small operations module; do not spread scheduling decisions through DOM
event handlers.

```text
RocketType
  id, name, stageCount, stages[], payloadLimit, defaultProfileId,
  createdAt, archived

FleetRocket
  id, typeId, padId, status, stageState[], assignedRouteId,
  activeMissionId, createdAt

MissionOrder
  id, source, destination, mode, fuelPolicy,
  outboundPayload, returnPayload, typeId, rocketId, profileId,
  currentLeg, status, createdAt

Route
  id, name, source, destination, mode, fuelPolicy,
  outboundPayload, returnPayload, typeId, profileId,
  enabled, autoLaunch, nextDirection, status, waitReason,
  completedLegs, failedLegs, createdAt, lastRunAt

FlightLogEntry
  id, missionId, routeId|null, leg, status,
  departedPadId, targetPadId, landingPadId|null,
  rocketId, rocketTypeId, rocketTypeSnapshot,
  payloadMass, profileId, elapsed,
  fuelStart, fuelUsed, fuelRemaining,
  revenue, fuelCost, structureCost, turnaroundCost,
  autopilotFee, cashDelta,
  touchdownVerticalSpeed, touchdownHorizontalSpeed, targetError,
  peak-load telemetry, completedAt
```

IDs are monotonically increasing within one game. Store IDs in relationships,
not object references. Mission launch snapshots all values that affect the
flight so later edits cannot change an active mission or history.

Keep transient presentation state (selected tab, open dialog, filter) outside
the simulation records. No DOM node or formatted string belongs in operations
state.

### State transitions

Centralize transitions and reject invalid ones without partial mutation:

```text
available -> queued -> flying -> turnaround -> available
                                -> lost
flying outbound -> landed/turnaround -> flying return -> complete
                                      -> return-blocked
```

Reservation, cash validation, and mission creation occur as one command. If
launch fails, release the rocket and leave cash unchanged. `mission.touchdown`
produces a structured result first; operations then updates fleet, route, log,
and UI from that result. Preserve `lastReport` as a concise current debrief,
but the flight log becomes the durable source of history.

A planet change starts a separate operations save for that world. No rocket,
route, or pad ID crosses worlds. Persistence across browser reloads is deferred
unless a small versioned `localStorage` adapter is added as a self-contained
final slice; correctness must not depend on storage being available.

## Implementation sequence

### Slice 1 — Structured flight records

- Expand flight start/end accounting into structured scalar fields.
- Add append-only flight-log entries for delivered, safe-wrong-pad, crashed,
  and return-blocked outcomes.
- Keep the current debrief generated from the same result so displayed text and
  stored numbers cannot diverge.
- Add deterministic IDs and timestamps through an injectable clock/ID helper
  for tests.

### Slice 2 — Rocket types and fleet lifecycle

- Extract the current builder config into named rocket-type snapshots.
- Add fleet instances, pad location, reservation, loss, refuel, and simplified
  turnaround commands.
- Make launch consume a mission order and a fleet rocket rather than mutable
  form controls.
- Preserve surviving stage/fuel state at touchdown instead of replacing the
  rocket before operations has processed it.

### Slice 3 — Dispatch UX and return missions

- Build the Dispatch view, pad highlights, swap behavior, validation summary,
  and autopilot-only send action.
- Implement two-leg mission progression with distinct directional payloads.
- Implement exact refuel and no-refuel policies; test launch blocking on the
  preserved return state.
- Add leg progress, return policy, and route identity to the flight HUD.

### Slice 4 — Flight log and route creation

- Build responsive, keyboard-usable log cards from structured records.
- Add **Create route from flight** with an explicit review step.
- Build route cards, edit/pause/delete actions, status reasons, and rocket-type
  replacement.

### Slice 5 — Scheduler and automation safety

- Add deterministic route readiness evaluation and atomic rocket reservation.
- Queue only one foreground flight, with confirmation by default.
- Add opt-in auto-launch, visible countdown/cancel, and pause while editing.
- Exercise competing routes for one rocket, wrong-pad landings, crashes,
  insufficient funds, and type changes while queued/flying.

### Slice 6 — Polish and optional persistence

- Add empty/loading/waiting states, compact mobile layout, focus management,
  live-region announcements, and reduced-motion behavior.
- If persistence ships, use one versioned per-world `localStorage` document,
  validate it on load, and recover to a fresh world without breaking startup.
- Update README controls/status and archive the plan with a measured worklog
  only after all acceptance criteria pass.

Maintain classic-script, `file://` compatibility. Operations may allocate when
a user creates/finishes a flight or edits a route, but the physics, per-frame
control, and render hot paths retain the existing no-allocation discipline.
The scheduler runs on state changes or at the operations deck, not every
physics step.

## Validation

Automated cases should include:

- every ordered pair of distinct pads, including wrap-around shortest paths;
- swap preserving directional settings correctly;
- duplicate Send clicks reserving/charging exactly once;
- one-way success, wrong-pad landing, and crash;
- return with refuel, including exact fuel loaded and ledger charge;
- return without refuel using the measured remaining state, both successful
  and launch-blocked;
- outbound payload unloaded and return payload loaded exactly once;
- two routes competing for one rocket with stable FIFO selection;
- a one-way rocket remaining at its destination;
- route waiting and then becoming ready when a matching rocket arrives;
- type changes while idle and rejection while a leg is flying;
- deleted/archived types restored from a flight snapshot;
- crash making a rocket unavailable and incrementing route failures;
- log retention without corrupting route counters;
- all existing manual-flight and autopilot envelope suites.

Use DOM smoke fixtures to verify tab semantics, labels, disabled explanations,
focus restoration after dialogs, keyboard activation, and narrow viewport
layout. Keep the existing multi-frame-rate autopilot tests for every dispatched
leg; operations must not bypass the common controls or alter flight physics.

## Acceptance criteria

- A player can choose any distinct start/end pad pair and immediately see
  whether a compatible rocket is available at the start.
- One click sends one validated mission on autopilot, with no duplicate charge
  or reservation.
- A return mission flies both directions in order. Refuel mode charges only the
  fuel loaded; no-refuel mode preserves outbound fuel/stages and never resets
  them secretly.
- Every finished leg, including failures, appears in a durable in-session log
  with route/build snapshots, measured flight data, and itemized cash fields.
- A completed flight can pre-fill a reviewed route. Enabling that route waits
  for the configured rocket type and payload conditions, then dispatches only
  when the foreground simulator is free.
- Routes have understandable statuses, can be paused/deleted, and can change
  rocket type while idle without mutating history or active flights.
- Automatic launch is opt-in, cancellable, and never steals focus from an open
  workshop/dialog.
- The UI is usable by keyboard and at phone width, has informative empty and
  blocked states, and does not require reading the canvas to operate it.
- Existing physics, manual controls, envelope limits, staging authority,
  touchdown adjudication, and reference-route outcomes remain unchanged.

## Deferred

- Route profitability forecasts, charts, ROI/depreciation, and optimization.
  The log schema deliberately captures their future inputs.
- Contracts, cargo scarcity, market prices, warehouses, and customer deadlines
  from 0.4. The provisional payload provider is replaced there.
- Part-level inventory, repair duration, wear, failures, and background rival
  flights from 0.4–0.5.
- Concurrent/background flight simulation. 0.3.5 queues routes around one
  visible deterministic simulation.
- Cross-world routes or transferring rockets between planets.
- Cloud saves, account sync, and multiplayer dispatch.
