# Plan 0.7 — Gameplay-Oriented Self-Explained GUI

Subject scope: make the operations deck and the flight HUD explain
themselves through visible state, ranked numbers and live checklists,
instead of through help text the player has to read. No new physics,
no second economy model, no per-frame allocation. Every number the
new panels show is computed from the same market, parts, rocket and
operations rules the dispatch already uses; the new planner module
only reads those rules and ranks the results.

This plan ships in one increment:

- **0.7.1 Self-explained deck & HUD** — profit opportunities ranked
  by profit and profit per minute, a visual pad picker, a delta-v vs
  payload plot in the workshop, an explicit manual launch path next
  to the autopilot launch, a flight HUD that shows remaining delta-v,
  vertical speed, cargo and per-stage fuel, and predicted profit per
  time on routes.

## Files

```
js/planner.js              # pure ranking: opportunities, dV curve, time estimate
js/rocket.js               # remainingDeltaV(state) for the HUD
```

## 0.7.1 — Self-explained deck & HUD

### 1. What can be delivered, and where the profit is

`js/planner.js` is a read-only layer over `market`, `parts`,
`operations` and `flightLog`. It allocates only when called from the
deck (never inside the frame loop) and returns plain records the
deck renders as rows.

- **Standing opportunities.** For every ordered pad pair, the cargo
  that fits is `min(type payloadLimit, destination demand)`. The
  reward is the standing-service quote at the destination's live
  price with the distance bonus; the cost is a full fuel load at the
  departure pad's fuel price. Profit is the reward less the 10%
  autopilot fee (or the full reward for a manual flight) less that
  fuel cost. Rows are ranked by profit, with profit per minute as
  the tie-breaker and a second sort by profit per minute.
- **Contracts.** Every open contract is ranked the same way, with
  its posted rate and its own payload. A contract whose payload
  exceeds the selected type's bay is marked `NEEDS BIGGER ROCKET`
  and names the smallest other type that fits it, so the player
  sees which builds unlock which work instead of discovering it by
  a refused dispatch.
- **Time estimate.** A leg's predicted time is the measured average
  `elapsed` of finished legs between the same two pads when the log
  has one, otherwise a distance heuristic calibrated to the shipped
  envelope (about 45 s for a 5 km hop, 63 s for 10 km on Verdant at
  1x). Profit per minute is profit divided by that time. The
  estimate is labelled as predicted; the log's measured cash and
  time stay the record.
- **Deck surface.** The Market tab opens with a "Best trades now"
  list: the top standing routes and contracts for the selected
  rocket type, each row showing route, cargo, reward, cost, profit,
  profit per minute and a fit badge. Clicking a row loads it into
  Dispatch exactly as loading a contract does today. The Dispatch
  summary gains a profit-per-minute row and a capacity-vs-demand
  bar, so "why not more payload" is visible: the bar stops at the
  smaller of the bay and the destination's appetite.
- **Type comparison.** Under the rocket-type select, Dispatch lists
  every type with its bay, its delta-v at the selected payload and
  its predicted profit on the current route. The selected row is
  highlighted; clicking another row switches the type. A type that
  carries more than the destination wants is marked `OVER DEMAND`
  instead of silently clamping the slider.

### 2. Pad selection and building

- **Visual pad picker.** Dispatch gains a pad row above the From/To
  selects: one card per pad showing fuel price, delivery price,
  appetite per leg, rockets present and deliveries served. Each
  card has `From` and `To` buttons that set the dispatch form and
  keep the map highlight in sync. The selects remain for keyboard
  and screen-reader use; both write the same form state.
- **Delta-v vs payload plot.** The workshop draws a canvas plot of
  delta-v against payload for the draft build: the curve is sampled
  with `rocket.evaluateBuild` at stepped payloads, the design
  payload is marked with a dot, and the payload limit is a vertical
  line. A caption quotes delta-v at the design payload, the limit,
  and the launch TWR, so the trade-off (more cargo, less delta-v)
  is read off the curve rather than from a single number. The plot
  is redrawn on workshop input only, never per frame.
- **Collapsible sections.** Dispatch steps, the pad picker and the
  type comparison are `<details>` sections that start open; the
  milestone ladder already folds. Folding never changes form state.

### 3. Manual launch next to autopilot

Today every dispatch enables the autopilot in `mission.beginLeg`,
so the only launch is automatic and the manual controls are
discoverable only by pressing `A` mid-flight. The dispatch gains an
explicit launch-mode choice:

- A segmented `Autopilot | Manual` control and two launch buttons:
  `Send on autopilot` and `Fly it yourself`. Both run the same
  `operations.evaluateLeg` gate; the manual path skips the profile
  lock (there is no profile to lock) and pays no autopilot fee.
- `operations.dispatch` carries `manual` on the order;
  `mission.beginLeg` honours it by leaving the autopilot disabled,
  the throttle at zero and the nose up, with `usedAutopilot` false.
  A return leg of a manual order is manual too, sent from the same
  return card.
- **Steps checklist.** The top of Dispatch is a four-step stepper
  with live state: pads chosen, rocket ready, mode chosen, launch.
  A step is checked when its condition holds, so the procedure is
  the panel itself. The old one-line help is replaced by this
  stepper plus the mode control.
- **In flight.** The flight strip gains a visible `Take over (A)` /
  `Hand back to autopilot (A)` button next to `Open deck`, so the
  handoff is a button as well as a key. The HUD mode row names the
  current pilot (`AUTOPILOT · BALANCED` or `MANUAL · YOU FLY`).

### 4. Flight HUD

The canvas telemetry panel keeps its existing rows and gains the
ones a pilot needs to fly without guessing:

- **Vertical speed** with an up/down arrow and the world's landing
  limit beside it, coloured green inside the limit and red above
  it. Horizontal speed stays beside it.
- **Cargo**: payload mass, `FRAGILE` when the leg carries fragile
  cargo, and the quoted payout at risk.
- **Delta-v remaining**: ideal staged delta-v left in the attached
  stack (`rocket.remainingDeltaV`), with a bar against the delta-v
  the stack launched with, so "how much is left" is a length, not
  a number to compare in memory.
- **Stage list**: one row per stage slot with fuel mass and a fuel
  bar; the burning stage is highlighted, spent stages are dimmed,
  and the next stage names the key that lights it (`SPACE` in
  manual, `AUTO` under guidance). Total fuel stays as its own row.
- **Aim guide**: the map draws a nose-direction tick and a velocity
  vector from the rocket, plus an arrow toward the target pad, so
  "where am I pointing vs where am I going" is drawn. The aim row
  names the source (`MOUSE` in manual, `AUTOPILOT` under guidance).
- The panel grows taller; on narrow viewports it keeps the existing
  repositioning rule and never leaves the screen.

### 5. Routes and predicted profit per time

- Each route card shows predicted profit per leg and predicted
  profit per minute for its next leg (planner estimate at current
  prices), plus the measured average cash per leg and average time
  from the log when the route has flown. Predicted and measured
  are labelled as such and never mixed.
- The route-review dialog shows the same predicted pair for the
  route being saved, updated when its pads, payload or type change.
- Dispatch shows predicted profit per minute for the current
  selection, so a route is planned against the same number the
  route card will later quote.

## Tuning and validation

- No physics, market or balance tuning changes. The planner's cost
  model (full fuel load, no turnaround or repair) is an estimate
  for ranking; the dispatch card's evaluated cost stays the number
  that is charged. The time heuristic is calibrated to the recorded
  envelope and is overridden by measured log averages as soon as
  they exist.
- `node experiments/planner-test.js` checks the planner against the
  real rules: dV curve matches `evaluateBuild`, standing quotes
  match `market.quote`, ranking is by profit, contracts that do not
  fit are flagged with the type that fits, and the time estimate
  prefers log averages.
- `node experiments/render-smoke-test.js` covers the new deck ids,
  the manual dispatch path (autopilot stays off, no fee), the
  flight HUD rows and the workshop plot. All existing suites must
  keep passing unchanged in behaviour; the manual flag defaults to
  false everywhere it is not set.
